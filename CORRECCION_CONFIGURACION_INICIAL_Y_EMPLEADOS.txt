1. PROBLEMAS ENCONTRADOS
------------------------------------------------------------------------------------------
A. «Empleao»
   Se buscó en todo el código fuente, la interfaz compilada (frontend/dist), la interfaz de
   escritorio (desktop/ui), el backend empaquetado (desktop/src-tauri/binaries y target), la
   documentación, el historial completo de git (git log -S «Empleao», todas las ramas) y la base
   de datos local (backend/data/pospy.db, solo lectura). No aparece en ningún sitio.
   La interfaz ya decía «Empleado» en todos los puntos visibles (rol en la barra superior, tabla
   y diálogo de usuarios, mensajes de validación del backend). No hubo nada que corregir.
   Si lo vio en pantalla, probablemente era una versión instalada más antigua o un dato escrito a
   mano (por ejemplo, el nombre de un usuario). En ese caso, indique dónde aparece.
   Identificadores internos: el rol se guarda como 'employee' (inglés, correcto). No se renombró
   ninguna tabla, columna, ruta ni variable.

B. El programa exigía crear una cuenta con contraseña desde el primer arranque.
   La pantalla de instalación obligaba a crear un administrador con contraseña. Después, siempre
   pedía usuario y contraseña. No existía forma de configurar antes la empresa ni de trabajar sin
   inicio de sesión.

C. Empleados.
   - Un empleado solo podía existir como cuenta con usuario y contraseña obligatorios.
   - El usuario no se podía cambiar después de crearlo.
   - No existía ningún módulo de tareas en el sistema: no había tablas, rutas ni pantallas de
     tareas. Por eso no se podía relacionar a un empleado con sus tareas.

D. Encontrados durante las pruebas (ya existían antes de este trabajo):
   - Preferencias: al abrir /configuracion directamente, la respuesta de /api/prefs podía
     llegar después de que la persona eligiera un tema. Entonces sobrescribía la elección sin
     guardar, y al pulsar «Guardar» se guardaba el tema anterior. Se reprodujo en la prueba de
     extremo a extremo (2 de 6 ejecuciones).


2. CAUSA RAÍZ
------------------------------------------------------------------------------------------
- AuthService.needs_setup() era «no hay usuarios». La única salida de ese estado era crear un
  administrador con contraseña (setup_admin). No existía ningún estado de configuración del
  acceso: ni «inicio de sesión activado o desactivado», ni «asistente terminado».
- Toda la API exige una sesión (cookie) ligada a un usuario. Sin cuenta con contraseña no había
  sesión posible.
- users.password_hash es NOT NULL y la creación de usuarios exigía contraseña y política.

4. CAMBIOS REALIZADOS
------------------------------------------------------------------------------------------
Modelo de datos — migración 3 (solo agrega; no modifica ni borra datos)
  - sessions.open_mode (0/1): marca las sesiones abiertas sin contraseña.
  - settings['acceso'] = {login_enabled, setup_completed, setup_step}.
    Si la base ya tiene usuarios, la migración guarda {true, true, 'listo'}: la instalación
    existente sigue igual que antes (inicio de sesión obligatorio).
  - Tabla tasks (título, descripción, responsable, estado, fecha límite, autor, fechas, versión).
    Un trigger impide borrar tareas; las tareas se cancelan.
  - Un empleado sin cuenta se guarda con password_hash = ''. Esa cadena vacía nunca coincide con
    ninguna contraseña. No hizo falta cambiar la columna.
  - Reversión: v003_access.DOWN_SQL (restaure antes una copia de seguridad).

Empleados
  - Alta sin cuenta: basta el nombre. El usuario se genera solo («Ana María Pérez» →
    ana.maria.perez, sin duplicados: luis, luis.2…). Opción «Crear cuenta de acceso».
  - A un empleado sin cuenta se le puede crear la cuenta después («Crear cuenta» con una
    contraseña temporal).
  - El usuario, el nombre, el rol, el estado activo y los permisos se pueden editar.
  - Desactivar no borra nada: los usuarios ya tenían un trigger que impide borrarlos.
  - El diálogo de cada empleado muestra sus tareas asignadas. Sus responsabilidades son sus
    permisos y sus tareas.
  - Tareas: con el permiso «tareas.gestionar» (los administradores lo tienen) se crean, asignan y
    editan. Sin ese permiso, cada persona ve solo sus tareas y solo puede cambiar su estado. No se
    asignan tareas nuevas a empleados inactivos; las que ya tenían se conservan y se pueden
    reasignar.


5. FUNCIONAMIENTO DEL NUEVO FLUJO
------------------------------------------------------------------------------------------
Primera ejecución
  1. La aplicación abre «Bienvenido a POS-PY» sin pedir cuenta.
  2. Hace falta el código de instalación de un solo uso. En el escritorio (Tauri) llega solo por
     el fragmento #setup=… y el asistente abre directamente. En el navegador se lee del archivo
     <datos>/setup-code.txt.
  3. Se crea el perfil «admin» (Administrador) sin contraseña, con una sesión de asistente.
  4. Pasos: Empresa › Preferencias (ventas e inventario) › Seguridad › Empleados › Finalizar.
     Cada avance se guarda en el servidor (setup_step).
  5. Seguridad: estado actual, activar o desactivar el inicio de sesión, cambiar el usuario y el
     nombre de la cuenta administrativa, asignar o cambiar la contraseña, y el cierre de sesión
     automático (inactividad, duración máxima, intentos y bloqueo).
     No se puede activar el inicio de sesión mientras no exista un administrador activo con
     contraseña: el botón está deshabilitado y el servidor también lo rechaza.
  6. Empleados: alta y edición con permisos, con o sin cuenta.
  7. Finalizar: se borra el código de instalación.
     - Con el inicio de sesión activado, se cierran las sesiones sin contraseña y se pide ingresar.
     - Con el inicio de sesión desactivado, se entra directamente al sistema.

Ejecuciones posteriores
  - Inicio de sesión activado: pantalla «Iniciar sesión».
  - Inicio de sesión desactivado: «¿Quién está trabajando?». Cada persona elige su perfil y
    trabaja con SUS permisos. Los administradores con contraseña la siguen necesitando: se abre
    el formulario de ingreso con su usuario. El botón «Salir» pasa a ser «Cambiar de perfil».
  - Asistente incompleto: continúa en el último paso guardado. Si el administrador ya tenía
    contraseña, se pide ingresar con ella y luego se retoma el asistente.
  - Los cambios posteriores se hacen en Gestión › Sesiones y seguridad (enlazado desde
    Configuración) y en Gestión › Empleados, usuarios y permisos.


6. MEDIDAS DE SEGURIDAD IMPLEMENTADAS
------------------------------------------------------------------------------------------
- Contraseñas: hash scrypt con sal aleatoria (ya lo usaba el proyecto). Nunca se guardan en
  texto plano ni en localStorage; la sesión es una cookie HttpOnly y SameSite=Strict. No se
  cambió a Argon2id ni a bcrypt: scrypt es una función de derivación resistente a hardware que
  OWASP acepta junto a esas dos, y cambiarla obligaría a volver a calcular todos los hashes.
- Todos los permisos se validan en el backend; la interfaz solo oculta lo no autorizado.
  Activar o desactivar el inicio de sesión, el asistente y la configuración de seguridad exigen
  ser administrador: tener «gestion.configuracion», que nunca se puede asignar a un empleado, y
  además rol de administrador.
- No se puede activar el inicio de sesión sin un administrador con contraseña. Con el inicio de
  sesión activado, tampoco se puede desactivar ni degradar al último administrador con
  contraseña. Así el sistema nunca queda sin nadie que pueda entrar.
- Desactivar el inicio de sesión solo cambia el indicador. No toca usuarios, contraseñas,
  permisos ni tareas (verificado comparando la base antes y después).
- Al activar el inicio de sesión se revocan las sesiones directas existentes. Además, cada
  petición vuelve a comprobarlo, por si quedara alguna sesión abierta.
- El acceso directo, el asistente y la consulta de perfiles solo se aceptan desde el propio
  equipo (loopback). Desde la red siempre se exige contraseña.
- La lista de perfiles no expone hashes ni datos sensibles: solo id, nombre, rol y si pide
  contraseña.
- Un usuario sin cuenta no puede iniciar sesión con contraseña. El intento recibe el mismo
  mensaje y tarda lo mismo que una contraseña errónea, para no revelar qué usuarios no tienen
  cuenta.
- El asistente exige el código de instalación de un solo uso (comparación en tiempo constante),
  que se borra al terminar.
- Todo queda en la auditoría inmutable: instalación iniciada y completada, inicio de sesión
  activado o desactivado, inicio directo, contraseña asignada, tareas.

8. LIMITACIONES PENDIENTES
------------------------------------------------------------------------------------------
- Protección local, no de servidor. Con el inicio de sesión desactivado, la seguridad depende
  de quién tiene acceso físico al equipo. Un administrador SIN contraseña puede ser elegido por
  cualquiera en ese equipo; la interfaz lo advierte en Seguridad. Asigne siempre una contraseña
  al administrador. Nadie protege el archivo de la base frente a quien tenga acceso
  administrativo a Windows: use una cuenta de Windows con contraseña y BitLocker.
- Detrás de un proxy inverso en el mismo equipo, todas las peticiones parecen locales y el
  acceso directo quedaría expuesto a la red. Active el inicio de sesión antes de publicar el
  servicio así (ya estaba documentado para la instalación inicial).
- Para retomar el asistente después de cerrar la aplicación vuelve a hacer falta el código de
  instalación. En el escritorio es automático (se genera uno nuevo en cada arranque); en el
  navegador se lee de setup-code.txt.
- Las contraseñas siguen con scrypt (ver punto 6), no con Argon2id ni bcrypt.
- El módulo de tareas es básico: no tiene notificaciones, prioridades, comentarios ni adjuntos.
- La migración 3 no tiene reversión automática. DOWN_SQL documenta los pasos manuales y
  requiere SQLite 3.35 o posterior para DROP COLUMN; lo recomendado es restaurar una copia de
  seguridad.
- No se probó manualmente el instalador de escritorio (Tauri/NSIS). El flujo con el código
  inyectado se verificó en la prueba de extremo a extremo con POS_SETUP_CODE, que es el mismo
  mecanismo.
